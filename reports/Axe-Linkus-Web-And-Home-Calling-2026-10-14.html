Axe on CallBox: Linkus web and home calling

14 October 2026 · CallBox (callbox.servicesuitecloud.com, now served from servicesuite-in, .228) · Axe Micro-Enterprise's P550

1. What changed

  • Linkus web inside the Riri phone. On a P-Series floor whose supervisor picks Browser phone — Linkus web in the Riri phone, the dock at the bottom right signs the agent's tab in as their extension, through the PBX's web port (8088, already open). Pressing Call anywhere on the desk opens the dock and dials from it. The PBX itself places the call, exactly as Linkus does.
  • Two ways to take calls, chosen by the supervisor. Settings → Connections → How agents hear their calls: the browser (Linkus web), or the agent's own phone (MicroSIP, desk handset, Linkus app). An agent can still switch for themselves from the dock (Use desk phone / Use browser).
  • Dispositions in the dock. When an Axe call ends, the dock offers ConnectBoxAXE's own outcomes, with the same rules: a promise needs an amount and a day, and a follow-up proposes its time. Saving records the outcome on the ConnectBox record, as the case file's pad does, and closes the pad on the case file.
  • Importing ConnectBox's people. Settings → Seats → Bring people in from ConnectBox lists every active ConnectBoxAXE agent and supervisor, then imports them in one click. Each gets a login by the same email, a seat on their ConnectBox extension, and the link to their ConnectBox id. They sign in with the password they use today; ConnectBox's own login checks it the first time. Axe's door asks for no SMS code.
  • The sign is created on the server. ConnectBoxAXE puts the PBX's Linkus SDK key inside its web page, and every agent's browser takes one of the PBX's eight tokens. CallBox keeps one token on the server and gives each agent a sign for their own extension only.

2. Your steps, in order

  1. On .228, switch writes on (the "Reading only" banner; the dock's dispositions need it too). In an elevated PowerShell:
    [IO.File]::AppendAllText("C:\LmsNode\lms.env", "`r`nCONNECTBOX_WRITES_AXE=true`r`n")
    Restart-Service LmsWeb
    Vercel had this switch as a "sensitive" value, which Vercel never shows back. So it never reached lms.env during the move. AXE_DESK_PAY_ENABLED and AXE_SERVICESUITE_CREATED_BY were lost the same way, so Axe's M-Pesa prompt is off until you add them.
  2. On the PBX: Integrations → Linkus SDK. It is already on, because ConnectBoxAXE uses it. Copy the AccessID and AccessKey. Our API app (Client ID …Yl4K) is refused sign creation (PBX error 10005), so the browser phone needs this second key.
  3. CallBox → Settings → Connections → Phone system: paste the AccessID and AccessKey into the Linkus web box, set How agents hear their calls to Browser phone — Linkus web in the Riri phone, then Save.
  4. CallBox → Settings → Seats → Bring people in from ConnectBox: read the plan (who is new, who is linked, any extension that changes), then press Import.
  5. Test from home: open the dock. The line should read Linkus web · ext 1010 ready (the browser asks for the microphone once). Open an Axe account and press Call. The dock opens and dials. When the call ends, save the outcome in the dock.
One Linkus web sign-in per extension. If an agent is still signed in to Linkus in ConnectBoxAXE and opens CallBox, the newest sign-in wins and the other one is signed out. The dock then says "signed in somewhere else", with a Sign in again button. Move each agent across fully rather than running both.

3. Calling from home

A. Linkus web (recommended): no router change expected

Signalling and SIP travel over wss://pbx.axemicroenterprise.co.ke:8088, which the internet can already reach. Voice uses the PBX's RTP ports. Axe's agents already talk through Linkus web to a PBX that isn't in their office (nine were signed in on 14 Oct), so voice already crosses Axe's router. Extension 1010 is set up exactly like a working agent's: Linkus web client on, NAT on. If a call connects but you hear nothing, forward the RTP range below.

B. MicroSIP from home: three changes on Axe's side

WhereChangeWhy
Router in front of the PBXForward UDP 5060 (SIP) and UDP 10000–12000 (RTP, the P-Series default; check PBX → Settings → PBX → SIP → RTP ports) to the PBX's LAN address. Where the router allows it, accept 5060 only from known IPs (your home is 41.90.172.32 today; home IPs change).From the internet only TCP 8088 answers today. SIP OPTIONS on UDP 5060 got no reply on 14 Oct.
PBX → Extension 1010 → SecurityTick Allow Register Remotely (it is 0 on 1010 and on the agents' extensions). Optionally limit it to allowed IPs.Without it the PBX refuses a SIP registration from outside its LAN, even with the ports open.
PBX → SIP settings → NATSet the public address to pbx.axemicroenterprise.co.ke (41.139.138.63) and list the PBX's local networks.So the PBX gives remote phones its public address for voice. Otherwise there is one-way or no audio.

Protect the open SIP port: switch on the PBX's IP auto-defence, allow Kenya only (Security → Allowed country IPs), keep strong registration passwords, and keep international calling off (it is off on 1010).

MicroSIP account: SIP server and domain pbx.axemicroenterprise.co.ke, username and login 1010, password = 1010's Registration Password (PBX → Extension → 1010; not the web login), transport UDP, keep-alive 15 s. MicroSIP on this PC is set to auto-answer all calls. That suits click-to-call, but it also answers inbound calls on its own.

4. Clear audio

ConnectBoxAXE's Linkus was noisy for reasons in its own code. The Riri phone does each of these differently:

ConnectBoxAXEThe Riri phone
Plays its own 440/480 Hz ring tone over the network's real ringback and Safaricom's announcementsNo synthetic tones: the agent hears the network's own early media; the screen says "ringing"
Beeps a call-waiting tone every 3 s into a live conversation when a second call arrivesCall waiting off: a second call never rings over the customer; the PBX treats the agent as busy
Uses whatever microphone settings the SDK asks forEcho cancellation, noise suppression and automatic gain set explicitly, mono, on the headset the agent chose
Can register the same extension in several tabsOne tab holds the phone. Other tabs stand by and take over only when it's free, so there's never a double ring or double playback.
No record of line qualityEvery Linkus call stores the SDK's own measurements: packet loss and jitter each way, the codec and the ICE result

On the floor: a wired USB headset, not laptop speakers; a wired connection or strong Wi-Fi; nothing large downloading during calls. If the stored figures show loss above about 2% on a line, that link is the cause. Putting OPUS ahead of G.711 for WebRTC on the PBX would then help, because Opus covers lost packets and G.711 does not.

5. What was verified, and what was not

  • Verified: the type-check, 43 telephony tests, 54 dialler tests and 80 Axe-floor tests pass, plus a production build. The PBX allows cross-origin requests from CallBox (Access-Control-Allow-Origin: *). CallBox sends no Content-Security-Policy that would block the SDK. ConnectBox's login API answers again. Extension 1010 has the Linkus web client switched on.
  • Not yet tried end to end: a browser signing 1010 in and placing a call. That needs the Linkus SDK key from step 2, and only you can paste it. Step 5 is that test.
  • The import runs on .228 beside the database. It cannot be run from a workstation, because the production database is no longer on Supabase.
