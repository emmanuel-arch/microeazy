The headline

The hard problems are behind us. A serverless deployment now reads a database that has no internet route, a bureau answers from a registered address, and one sign-in opens six front doors. What remains is not infrastructure — it is that three of the six systems are still reading the wrong database.

04

Twelve findings, in the order they should be fixed

each reproduced today
Blockers — one variable and one column stand between us and the exchange
F1

The relay cannot read Micromart Fintech

Blocker

relay-host/.env.example never mentions MICROMART_FINTECH, and warmPools() in sql-relay.ts warms only micromart and axe. Both Interchange members on that server — 3005 and 3002 — resolve through the micromart-fintech org, so a single absent variable takes out half the exchange.

$ npm run interchange:members
Micromart (services) unreachable — SQL relay returned 503.
"The relay host has no connection string for Micromart Fintech."
F2

Half the Interchange membership is unpublished

Blocker

NODE_MEMBERS declares four. The deployed registry serves two: Fintech (79 tokens) and Axe Boresha (14,149), both built 26 August. Missing is KE/LENDER/3002 — Micromart Africa, 142,393 borrowers, the anchor member the whole exposure argument rests on. Consequence of F1; fixed by re-running the publish once the variable is set.

F3

The group roll-up crashes on Axe's server

Blocker

getGroupBook() selects onboardingLatitude / onboardingLongitude. Axe's Serviceconnect predates those columns, so the one analytics surface that does read live throws on the second-largest book in the ecosystem. Guard the two terms with COL_LENGTH().

AXE — ERR Invalid column name 'onboardingLongitude'.
Live-data gaps — the reason this document exists
F4

The Analytics Studio aggregates the wrong database

Major

Fourteen of fifteen surfaces call headline, timeSeries, cube or cohorts in lib/analytics/engine.ts, which groups in Postgres through orgTx. For Micromart that is a 199-loan book, so the board view will greet the room with "There is no open book in this cut." The studio's entire data surface is those six functions — which is also why it is tractable in a weekend.

F5

Four console dashboard panels stay modelled forever

Major

MODELLED_PANELS = ["series","aging","productMix","branches"]. applyLive() overlays real KPIs and then sets simulated: false — true of the headline figures, false of the time series, the aging buckets, the product mix and the branch table, which are still produced by a seeded PRNG. The screen labels each region honestly, which is the right behaviour and still not a thing to project.

F6

The borrower's own loan screen refuses bridged lenders

Major

/api/portal/my-loan returns bridged: true and the message "Your Micromart loan is managed on the lender's own system." A real Micromart borrower opening the ecosystem's My-loan screen is deflected. Same for /api/portal/ladder, which counts Postgres rows. Both live equivalents are already written and tested — getCustomer360() and checkGraduation() — so this is wiring, not new SQL.

F7

Console operations screens read Postgres

Accept

Applications, loans, collections, disbursements, repayments, products and workflows all resolve locally. This is correct — they are origination surfaces for a book we originate, and Micromart originate in their own core. It is nonetheless 24 screens that must not be opened on a Micromart session during the demonstration. Drive origination from Mular Credit instead, where the book is genuinely ours.

F8

Interchange scoring and learning run on seeded holdings

Accept

seed-holdings.ts and seed-ledger.ts build the overlapping population, the bitemporal ledger, the decision history and the declined applicants that reject inference recovers. The exposure engine itself queries the two live members. Say the distinction out loud on the Score and Learning screens rather than letting somebody find it.

Hygiene — small, cheap, and each one is visible from the room
F9

The artwork check reports a failure that is not one

Cosmetic

verify-live.ts probes six .png masters; artwork.ts serves .webp. PeopleHub's master is a .jpg, so the PNG 404s and the run reports "5/6 artworks". All six doors serve their plate — confirmed 200, 9,884 bytes. Point the check at the file the app reads.

F10

The relay-host bundle is untracked

Risk

Eleven files — the host-verification script, the service installer, both relays and the failure taxonomy — exist only on this laptop. They are the deployment that makes the cloud work, and the document that explains what to do when it stops. Commit them.

F11

The ecosystem registry says two systems are not deployed

Cosmetic

registry.json carries live: false for the Interchange and the PWA, and a note that portal.servicesuitecloud.com has no DNS record. Both now answer 200 with their real titles. The registry is the file every script trusts; a stale one is how a fresh machine gets the wrong idea.

F12

Founding-cohort books are not reachable from the relay

Post-demo

Ten qualifying entities on the .198 server — NJB, Buy Simu, ATICO and seven more, ~43,000 borrowers between them — need SERVICESUITE_CONN_BUYSIMU on the relay host to join the exchange. Not demo-critical, and the single highest-value thing to do the week after.

08

What we will not claim

say it before it is found

The suite's credibility rests on every screen degrading honestly, and that only works if the person presenting does the same. Four things to name from the front.

  • PeopleHub has three empty tables and says so. Payroll, leave and contracts. We will not invent a payroll figure — and the reason to say that out loud is that it is the same promise that makes the balances trustworthy.
  • Their data stops in places. Promises end November 2024, tasks August 2025, call detail records September 2023. These are findings about their process, not gaps in ours. Show them; they are worth money to the room.
  • The Interchange's scoring and learning screens run on a seeded population. The exposure engine queries live member books; the model training history does not exist yet because the exchange is six days old. Name the boundary on the screen it applies to.
  • Nine indexes are proposed and none applied. loanSchedule (1.95m rows), Loans (338k), CallLogs (1.34m) and PayedAmount (1.15m) carry no indexes at all. It is their database, so it is their decision — and their own reporting is almost certainly paying the same tax.
