The USSD Channel

How Africa's Talking drives ATusersUssdApI, why a Micromart Fintech customer is offered Micromart Africa's menu, and what it takes to turn one lender's USSD app into something every Micro Eazy client can dial.

§ 0What was found

There is no hardcoded 3002. The string does not appear in the C# and it does not appear in any of the eight stored procedures the service calls. Micromart's report is accurate about the symptom and wrong about the cause, and that distinction matters, because the actual causes are four separate defects that a search-and-replace would not have touched.

Verified live Every figure in this document was read from Micromart's ServiceSuite database on 2 September 2026 through the Connected Suite's read-only connection. The queries are reproduced in the appendix.

What a Micromart Fintech customer sees when they choose Borrow Loan is a six-item category menu — BUSINESS LOAN-DAILY, SCHOOL FEES LOAN, SALARY LOAN and the rest. That list is Micromart Africa's product taxonomy. It is shown to the Fintech customer because the query behind it has no entity filter and the table behind that has no entity column. Four of those six categories contain nothing the Fintech book can sell. The customer picks one, gets a header with no options beneath it, and concludes the service is broken.

That is the presenting complaint. Underneath it the service has a deeper problem: it has no concept of which book it is serving. The entity is re-derived from the phone number at four separate call sites, by two different rules, one of which returns a literal zero for exactly the customers who most need it to be right. The PIN — the only credential in the system — is read and written with no entity filter at all.

15,472 borrowers hold a USSD PIN across the three books this service can reach. It is live and in daily use.

44 phone numbers exist in more than one book. Every one of them can neither borrow nor safely set a PIN.

§ 1How Africa's Talking USSD actually works

USSD is not a protocol you implement. It is a protocol Safaricom implements, Africa's Talking translates, and you answer. Your entire surface area is one HTTP endpoint that receives a form post and returns a string. Everything difficult about USSD follows from how little that string is allowed to be.

1.1 · The channel

Africa's Talking leases a service code from the operator and sublets a slice of it to you. Micromart's customers dial something of the form *384*NNNN#: *384# is the shortcode Africa's Talking operates on Safaricom, and NNNN is the channel assigned to a single application. You register one callback URL against that channel in the AT dashboard. From then on, every keypress by every customer on that code arrives at that URL.

That last sentence is the whole tenancy story, and section 6 turns on it: the channel is one-to-one with the callback URL, and the callback URL is one-to-one with a deployment. Two lenders on one deployment means two channels pointing at the same URL — which is fine, and is exactly how this becomes reusable, provided the code reads the field that tells them apart.

The dial string *384*NNNN# is an Africa's Talking sublet. A lender who wants their own *XYZ# must apply to the operator directly — months, and a fee. For every client after Micromart, an AT channel is the practical choice.

1.2 · The four fields

The gateway posts application/x-www-form-urlencoded with four fields. There are no others, and there is no body, no JSON, and no header worth reading.

FieldWhat it carries
sessionIdOpaque string, stable for the life of one dialogue, new on every dial. The only handle you get on "this conversation".
serviceCodeThe code the customer dialled. The tenant discriminator — see §6.1. This service reads it once, to write it to a log file.
phoneNumberMSISDN in +2547XXXXXXXX form. Asserted by the network, not by the handset — the one genuinely trustworthy field.
textEverything the customer has typed this session, joined by *. Empty on the first request.

1.3 · CON and END

You reply with text/plain. The first four characters decide what the handset does with the rest:

CON Enter your PIN └ input box shown · session stays open

The customer can type. Your next request will carry what they typed.

END Your loan balance is 4,500 └ message shown · session destroyed

No input box. The dialogue is over and the sessionId will never return.

There is no third option. There is no way to send a message and keep the session open without asking for input, no way to push a screen the customer did not ask for, and no way to reopen a session you ended. END is irreversible, which is why every error path in this service — including recoverable ones like a mistyped PIN — costs the customer the whole dialogue.

1.4 · The cumulative string is the state

This is the idea everything else rests on. Africa's Talking keeps no state on your behalf beyond the session's existence. Instead, every request re-sends the complete input history, asterisk-delimited, from the top.

A customer who dials in, enters PIN 1234, chooses Borrow Loan, picks category 2, product 1, and types 5000 generates six HTTP requests, each carrying strictly more than the last: 

  request   text=                   what you must return
  1         (empty)                 CON Welcome … enter your PIN
  2         1234                    CON 1. Check Balance / 2. Pay / 3. Borrow
  3         1234*3                  CON Select Category
  4         1234*3*2                CON Select Product Code
  5         1234*3*2*1              CON Enter Amount
  6         1234*3*2*1*5000         END Your request has been received
Consequence The service is stateless by construction. It never has to remember anything — but it also has to re-validate the PIN, re-resolve the customer, and re-establish which book it is in, on every single keypress. This service does exactly that, and it is where the entity bugs live.

Two properties follow directly. First, navigation depth is text.Split('*').Length — the service can route purely on how many selections have been made, which is precisely what HandleMainFlow does. Second, the PIN is re-sent in plaintext on every request and is re-verified against a bcrypt hash each time. Six requests, six bcrypt verifications, each deliberately costly. At work factor 12 that is real latency inside a session with a hard timeout.

1.5 · The screen budget

A USSD screen is capped at 182 characters by GSM 03.38, and handsets in the field routinely render less. Overflow is not wrapped or paginated — it is truncated, silently, by equipment you do not control.

Micromart's category screen, measured against the live table, is 159 characters. It fits, with 23 characters of headroom. Adding a seventh product category — a perfectly ordinary business request — overflows it and truncates the menu mid-item on some handsets. Any reusable version of this service has to treat 182 as a budget it enforces, with pagination as a first-class feature rather than something bolted on when a client complains.

chars CON Select Category: 21 1) BUSINESS LOAN-DAILY 22 2) BUSINESS LOAN-WEEKLY 23 3) BUSINESS LOAN-MONTHLY 24 4) SCHOOL FEES LOAN 19 5) SALARY LOAN 15 6) ASSET LOAN 14 0. Back 8 00. Exit 10 ───────────────────────────────────────── total 159 / 182

The live category screen. Every one of these six lines is drawn from a table with no entity column — see F1.

1.6 · Sessions end without telling you

The operator enforces a maximum session duration — on Safaricom Kenya this is conventionally around three minutes, and it should be confirmed for Micromart's specific channel rather than assumed. When it expires, no callback is made. Your service does not learn that the customer walked away; the requests simply stop.

The same is true of the per-request timeout. Africa's Talking waits a few seconds for your HTTP response and then abandons the session. This is the single most important operational constraint on the design, and it rules out exactly the thing a loan application wants to do: call a credit bureau, run a score, wait. Anything slow must be queued and answered with END … is being processed — which is, correctly, what this service does.

1.7 · What the gateway does not give you

You do not getWhat that means for the design
AuthenticationAT posts unsigned. Anyone who learns the callback URL can post any phoneNumber they like. Mitigation is IP allow-listing plus a shared secret in the path or a header — see F8.
IdempotencyA retried or duplicated request is indistinguishable from a real one. A booking endpoint reached at the last level of a menu must be idempotent on sessionId, or a network hiccup books two loans.
Delivery confirmationYou never learn whether your END screen was displayed.
Rich inputDigits and *. No letters in practice, no confirmation dialogs, no back button — which is why 0 and 00 have to be invented in application code.

§ 2How this service implements it

ATusersUssdApI is a single-controller .NET 9 web API — 936 lines across 16 files, one endpoint, no tests, no authentication, and a database contract of four tables and eight stored procedures. It is small enough to hold in your head, which is a genuine virtue and the main argument for porting it rather than rewriting from a specification.

2.1 · The request lifecycle

Every keypress from every customer enters at POST /ussd/service and runs the same six steps:

  1. Normalise the MSISDN. PhoneHelper.Normalize strips non-digits, takes the last nine, and prefixes 254. Correct, total, and — importantly — the same transformation the stored procedures apply internally, so the two agree.
  2. Log, if there is input. A file append to C:\Logs\ussd\. See F9: the writer is a singleton with no lock.
  3. Check PIN status. One query. If the borrower has no PIN yet, the request is diverted into the enrolment flow and never reaches the menu.
  4. First screen, or main flow. Empty text means the customer has just dialled: greet them by lender name and ask for a PIN.
  5. Split, normalise back/exit, validate the PIN. The PIN is parts[0], re-verified with bcrypt on every request.
  6. Route on depth. parts.Length selects one of five level handlers. This is the whole navigation model.
An honest strength Steps 1, 4 and 6 are well judged. Routing on parts.Length rather than on a persisted session cursor is the right call for a stateless gateway, and it is why the service survives an AT retry without corrupting anything.

2.2 · The one piece of server state, and why it barely matters

There is a UssdSession table, written by sp_ussdsession, which increments a level counter per (sessionId, phoneNumber). It is used for one purpose only: PIN enrolment, where the customer has typed a new PIN and a repeat, and the service needs to know which of the two prompts it is on.

Every other screen ignores it entirely and derives position from text. This is not an inconsistency worth fixing so much as one worth noticing: the enrolment flow could be derived from text too, and then the table — and the write on every enrolment keypress — disappears.

2.3 · Back and exit

USSD has no back button, so 0 and 00 are conventions the application invents. NormalizeParts implements them by rewriting history: it walks the parts array and pops the previous selection whenever it meets a 0. 

// text = "1234*3*2*0" → parts = [1234, 3] → back at the categories
for (int i = 1; i < rawParts.Length; i++) {
    if (rawParts[i] == "0") {
        if (list.Count > 1) list.RemoveAt(list.Count - 1);  // back
        else return (list.ToArray(), true);   // nothing to go back to → exit
    }
    else list.Add(rawParts[i]);
}

This is the cleverest code in the repository and it is correct. It has one consequence worth naming: 0 is reserved at every level, including the amount prompts. A customer who types 0 as a repayment amount goes back a screen instead. That is defensible — zero is not a valid amount — but a customer typing 00 as an amount exits the session, and neither behaviour is explained on screen.

2.4 · Two customer shapes, and only one of them works

sp_checkCustomerCompomany counts the borrower rows carrying this phone number and returns a sentinel:

Note what the count is not scoped by. It counts rows across every entity on a shared ServiceSuite instance — Micromart Africa, Micromart Fintech, Axe Capital, and anyone else who lands there. That is the root of F5.

§ 3The entity problem, measured

Micromart runs two books on one ServiceSuite instance: 3002, Micromart Africa Limited, the established SME lender, and 3005, Micromart Fintech, where the Micro Eazy products live. The entity is not a label on the data — it is an identity boundary, and the same phone number in the two books can belong to two different people.

Critical

F2

The PIN is read and written across every book at once

Critical

Enrolment writes the new PIN like this: 

new SqlCommand("UPDATE Borrowers SET USSDPIN = @pin WHERE PhoneNumber = @phone", con);
The overlap, exactly 44 distinct phone numbers span more than one book: 43 across Micromart 3002 and 3005, 2 across Micromart 3002 and Axe Capital 3003. One number appears in all three, which is why the pairs sum to 45.

No EntityId. No TOP 1. For a phone number present in two books, this overwrites the credential on both — including the row belonging to a different person. Validation has the mirror-image defect, reading SELECT TOP 1 UssdPin … WHERE PhoneNumber = @mobile with no entity predicate and no ORDER BY, so it authenticates against whichever book the query plan happens to reach first.

Forty-four numbers are in this position today. That is a small number and a serious one: the fix is one AND EntityId = @EntityId, and the consequence of leaving it is that one customer's PIN change silently changes another customer's PIN.

F3

Multi-book customers are asked for the products of entity zero

Critical

GetEntityId.EntityId has two behaviours. For a single-book customer it looks the entity up from Borrowers. For a multi-book customer it returns selectedEntity — the value the caller passed in — unchanged. Which makes the caller's argument load-bearing: 

// ServiceController.GetProducts — reached by BOTH customer shapes
int entityId = _getEntityId.EntityId(req.phoneNumber,
                                     customerStatus,
                                     0,        // ← the entity
                                     constr);

// For a MultiCompany customer, EntityId() returns this argument
// unchanged. So the proc runs as sp_ussdGetproducts @EntityId = 0
// and returns nothing — while the lender the customer actually
// selected sits unread in parts[1].

CheckBalance passes the same literal zero. It happens to be harmless there — the multi-book balance path is handled separately, one branch earlier — but it is the same latent mistake in a second place.

This is the closest thing in the repository to the complaint as reported. It is not a hardcoded 3002; it is a hardcoded 0. The effect is not that the customer gets the wrong book's products, but that they get a header and no products at all.

F4

A multi-book customer can never finish a loan application

Critical

The two customer shapes need different menu depths, because the multi-book customer spends one selection choosing a lender:

HandleLevel5 opens with if (customerStatus == CustomerStatus.SingleCompany) and has no corresponding multi-book branch, so it falls through to END Invalid selection. There is no HandleLevel6 at all; the router's default arm returns END Invalid input.

Combined with F3, the multi-book borrow flow is broken twice over — it shows an empty product list, and had the list been populated, the application could not have been submitted. The 43 customers who hold accounts in both Micromart books cannot borrow over USSD at all.

F5

One lender's customers are offered another lender's book

Critical

sp_checkCustomerCompomany counts borrower rows for a phone number with no entity restriction, and GetCustomerCompanies then lists every entity that number appears under, joined to BsEntity for the display name. Neither knows which lender's USSD code was dialled — because, as §1.2 noted, serviceCode is never read.

Two Micromart numbers also exist in Axe Capital's book. Those customers, dialling Micromart's code, are shown a lender menu that names Axe Capital, and selecting it queries sp_GetolbOrLoanLimit against entity 3003 — returning an Axe Capital loan balance to whoever is holding that SIM.

F6

The branch gate inside the product proc strands 529 Fintech borrowers

High

sp_ussdGetproducts applies a scope the C# has no idea exists. It looks up the borrower's branch and requires the product to list that branch: 

SET @EntityUnit = (SELECT EntityUnit FROM Borrowers
                   WHERE EntityId = @EntityId AND PhoneNumber = @Phone)

SELECT ID, ProductName, UssdOrder FROM Products
WHERE IsActive = 1 AND CategoryId = @CategoryId AND EntityId = @EntityId
  AND CHARINDEX(',' + CONVERT(VARCHAR(MAX), @EntityUnit) + ',',
                CONCAT(',', EntityUnits, ',')) > 0

Micromart Fintech's two USSD-visible products both carry EntityUnits = '0,129'. Its borrowers are distributed across four branches:

Branch (EntityUnit)BorrowersListed on the products?

35417no — empty menu

529 Fintech borrowers — 3.1% of the book — reach the product menu and are shown nothing, in the two categories that do have products. Nothing in the application layer can detect this: the proc returns zero rows and the app renders a header. Worse, if the borrower has no row for the entity being queried at all, @EntityUnit is NULL, the CHARINDEX comparison evaluates to NULL, and the predicate silently excludes everything — which is the mechanism by which F3's entity zero produces an empty menu rather than an error.

This is a data fix, not a code fix, and it should be Micromart's call: either add branches 1, 25 and 35 to the two products' EntityUnits, or move those 529 borrowers into branch 129. But the application should also stop rendering an empty menu — see §4.3.

F7

The KES 3,000 floor is enforced, then thrown away

High

sp_UssdInsertLoan declines anything under KES 3,000 and returns a row saying so. Its own header comment is explicit that the app ignores it — and it does: 

-- in the proc
IF (@Principal < 3000)
BEGIN
    SELECT 0 AS LoanID, 9 AS Code,
           'Amount applied must be at least 3000' AS Response;
    RETURN
END

// in the controller
cmd.ExecuteNonQuery();          // ← the decline row is discarded
return "END Your request has been received and is being processed.";

A customer applying for KES 2,000 is told their application succeeded. Nothing is booked, nothing is queued, and no one is notified. The floor is not surfaced anywhere on the amount screen either, so there is no way for the customer to have known.

The same procedure accepts a @SelectedPeriod parameter that the USSD flow never collects, so every USSD loan takes whatever tenor sp_InsertLoan defaults to. That is worth a conversation with Micromart before it is treated as a defect — it may be deliberate.

F8

The endpoint is open and the PIN has no attempt limit

High

POST /ussd/service has no authentication filter, no IP restriction, and no shared secret. Africa's Talking does not sign its posts, so something has to stand in for that, and nothing does. Anyone who discovers the URL can post any phoneNumber with any text.

They still need the PIN — but the PIN is four digits, there is no lockout, no attempt counter, and no rate limit. Ten thousand posts exhausts the keyspace for a chosen customer, after which the attacker can read balances, trigger STK prompts, and submit loan applications in that customer's name. Bcrypt at work factor 12 is the only thing slowing this down, and it was chosen to protect the hash at rest, not to serve as a rate limiter.

Three mitigations, in order of value: allow-list Africa's Talking's egress addresses at the firewall or reverse proxy; move the callback to an unguessable path segment carrying a shared secret; and add a per-MSISDN attempt counter that locks the PIN after five failures. The first two are configuration and can be done this week.

F9

Two smaller defects that will show up under load

Medium

The STK response is discarded. InitiateStkPush returns "Failed to retrieve STK parameters." when the entity has no Daraja row, and returns Safaricom's raw response body otherwise. InitiatePayment ignores the return value entirely and reports success unless an exception was thrown. A rejected STK push — wrong shortcode, expired passkey, throttled — reads to the customer as "Wait for the M-Pesa prompt". Both Micromart books currently have valid rows, so this is latent rather than active, and it will become active the first time a new lender is onboarded without one.

The log writer is not concurrency-safe. WriteLog is registered as a singleton and opens the day's file with FileShare.Read on every request that carries input — which is most of them. Two concurrent sessions means the second request throws IOException and returns a 500, which Africa's Talking renders to the customer as a dead session. This is invisible at low volume and guaranteed at high volume. It also writes to C:\Logs\ussd\, a hardcoded path that ties the service to a Windows host.

Relatedly, Payments constructs new HttpClient() per STK push, exhausting sockets under load. All three are standard fixes: a lock or a logging framework, and an injected IHttpClientFactory.

§ 4The fix

Every defect from F1 to F6 is the same defect wearing different clothes: the entity is re-derived, late, at each call site, instead of being resolved once and carried. This is precisely the shape of the bug already fixed in the borrower PWA, where four different notions of "entity" coexisted in one app and only one of them was right. The remedy there was a single module that owns the answer. The remedy here is the same.

4.1 · Resolve once, at the top, and carry it

The controller already has everything it needs by line 4 of HandleUssd: the normalised MSISDN, the service code, and the text. Resolve the book there, once, and pass it down. Nothing below should ever call GetEntityId again. 

/// The book this session is in. Resolved once per request, never re-derived.
public sealed record UssdContext(
    string Phone,
    int    EntityId,      // the book. Never 0, never guessed.
    int    EntityUnit,    // the branch — sp_ussdGetproducts needs it
    string LenderName,
    bool   MultiBook);

/// Resolution order, most authoritative first:
///   1. the entity the customer explicitly selected this session
///   2. the entities this SERVICE CODE may serve  (§6.1 — closes F5)
///   3. the borrower's own row, when there is exactly one
/// If none of those yields exactly one book, ASK. Never fall through to a
/// literal, and never to an unordered TOP 1.
Why this matters more than the individual fixes Patch F1–F6 one by one and they come back with the next feature. Introduce UssdContext and there is no longer a place to put the bug: there is one entity in scope and it was resolved before the routing began.

Two rules make the difference between this holding and quietly rotting again:

  1. An unresolved entity is an error, not a zero. The reason F3 was invisible for so long is that entity 0 produces an empty menu, and an empty menu is indistinguishable from "this customer has no eligible products". Fail loudly instead.
  2. No TOP 1 without an ORDER BY. There are three of them today, in GetEntityId, Login.ValidatePin and sp_CompanyName. Each returns whichever row the query plan reaches first, which is stable until the day an index changes and then is not.

4.2 · The C# changes

IDWhereChange

4.3 · The SQL changes

F1 and F5 cannot be fixed in C# alone. Both need the procedures to learn about the entity. 

-- F1: categories that actually contain something this customer can be sold.
-- New proc rather than an edit, so nothing else that reads ProductCategories
-- is affected. ProductCategories keeps no EntityId; Products supplies the scope.
CREATE PROCEDURE dbo.sp_UssdGetCategories
    @EntityId INT, @Phone VARCHAR(20)
AS
BEGIN
    DECLARE @Unit INT = (SELECT EntityUnit FROM Borrowers
                         WHERE EntityId = @EntityId
                           AND PhoneNumber = @Phone);

    SELECT DISTINCT c.ID, c.CategoryName
    FROM   ProductCategories c
    JOIN   Products p ON p.CategoryId = c.ID
    WHERE  p.EntityId = @EntityId
      AND  p.IsActive = 1
      AND  p.UssdOrder IS NOT NULL
      AND  CHARINDEX(',' + CONVERT(VARCHAR(MAX), @Unit) + ',',
                     CONCAT(',', p.EntityUnits, ',')) > 0
    ORDER BY c.ID;
END

Note what this does beyond fixing F1. Because it applies the same EntityUnits and IsActive predicates as sp_ussdGetproducts, a category can no longer be listed unless the product list behind it will be non-empty — which closes the user-visible half of F6 for free. A Fintech customer in branch 35 sees no categories at all rather than six that lead nowhere, and the service can say so plainly instead of showing a header over emptiness.

On the live data this reduces the Fintech category menu from six items to two — BUSINESS LOAN-WEEKLY and BUSINESS LOAN-MONTHLY — and the main book's from six to three. It also drops the screen from 159 characters to well under half the budget. 

-- F5: only the books this operator is allowed to serve.
-- @AllowedEntities is a comma list supplied by the app from the service-code
-- registry (§6.1), so Axe Capital can never appear on Micromart's shortcode.
ALTER PROCEDURE dbo.GetCustomerCompanies
    @phone VARCHAR(20), @AllowedEntities VARCHAR(200)
AS
BEGIN
    SET @phone = '254' + RIGHT(@phone, 9);
    SELECT bs.ID, bs.EntityName
    FROM   Borrowers b
    JOIN   BsEntity  bs ON bs.ID = b.EntityId
    WHERE  b.PhoneNumber = @phone
      AND  CHARINDEX(',' + CONVERT(VARCHAR(20), b.EntityId) + ',',
                     ',' + @AllowedEntities + ',') > 0
    ORDER BY bs.EntityName;
END

sp_checkCustomerCompomany needs the same treatment — its count must be restricted to the allowed entities, or a customer with one Micromart account and one Axe account will still be misclassified as multi-book and sent down the broken path.

Finally, the lender menu should present ordinals, not entity ids. A customer should key 1 or 2, and the service should map that back to the entity. Keying 3005 works today only because HandleLevel2 parses the keypress as an EntityId directly, which is also what makes the menu unsafe to reorder.

4.4 · What not to change

Leave these alone until someone confirms them

The EntityUnits data. Adding branches 1, 25 and 35 to the Fintech products makes 529 borrowers eligible for credit they are not eligible for today. That is a lending decision, not a bug fix. Surface it to Micromart and let them decide.

The @SelectedPeriod default. USSD loans currently take sp_InsertLoan's default tenor. Collecting a period on the menu changes the terms of every USSD loan booked afterwards.

The Triple-DES / MD5 Decipher. It is weak, and it is what the existing Stkparams ciphertext was written with. Replacing the algorithm requires re-encrypting live Daraja credentials for every entity; do that as its own migration, never as part of this work.

This is the same restraint applied to registerFCM in the PWA, where PhoneNumber: fcmToken looked like swapped fields but could not be corrected without knowing what the backend had actually been storing. Fixing what is provably wrong and flagging what merely looks wrong is the difference between a safe change and an outage.

§ 5Reuse this repository, or start a new one?

Both — in that order. Patch this one in place for Micromart, because it is carrying live traffic and 15,472 enrolled PINs. Build a new one for everybody else, because this one cannot be made multi-tenant without becoming a different program.

5.1 · Why not simply fix this one and reuse it

ObstacleWhy it blocks reuse
It is somebody else's repository skegode/ATusersUssdApI is upstream, the same relationship the ecosystem has with PBXAuthentication: tracked read-only, never pushed to. Every ecosystem change would be a pull request into a repo whose release cadence we do not control.
It is a single-tenant deployment artifact One connection string in appsettings.json, one log path, one publish profile pointing at a named person's Desktop. Adding a lender means a second deployment, a second server, a second set of credentials to rotate.
Tenancy is not a parameter anywhere serviceCode arrives on every request and is written to a log file. There is no registry, no per-tenant configuration, and no place to put one that is not a new module.
The menu is hard-coded C# Five level handlers with the menu tree expressed as switch arms and string concatenation. A lender who wants a different menu order needs a code change and a redeploy.
No tests, and a live channel underneath 276,518 loans on one book and 61,549 on the other, both booking today. Restructuring it is not a refactor, it is an outage risk.

5.2 · The recommendation

  1. Patch ATusersUssdApI in place, minimally. F2, F3, F5 and F1 — the four that are actively wrong for Micromart — plus the F8 configuration mitigations. No restructuring, no UssdContext refactor if it cannot be done safely, no new dependencies. Two to three days including a rehearsal against a copy of the database. This is the deliverable Micromart is asking for.
  2. Stand up micro-eazy-ussd as a new ecosystem repository. Multi-tenant from the first commit, registered in ecosystem/registry.json like every other system, with the tenant model of §6 rather than one bolted on later. Port the parts of this service that are genuinely good — and there are several — and rebuild the rest.
  3. Prove it on the second lender, not on Micromart. Point a new Africa's Talking channel at it for whichever client comes next. Micromart migrates only once the new service has run somebody else's book for a month. Their channel is the one thing in this picture that must not break.

5.4 · What to build it in

TypeScript, as its own small service. The reason to rebuild at all is to inherit the ecosystem's tenant discipline, and that discipline is already written down in connected-suite/src/lib/enterprise/connections.ts — an org registry mapping a slug to an EntityId and a connection string, resolved server-side, with the client never seeing a raw entity id. Rewriting that in C# to keep the .NET stack means maintaining two copies of the one thing that must never disagree.

Against that, one real constraint: USSD has a latency budget of a few seconds and no room for an extra hop. The Connected Suite reaches ServiceSuite over a relay when direct TDS is unavailable, and a relay round trip inside a USSD session is a session that dies. The new service should hold a direct TDS connection from a host with a route to the database, with the relay as failover only — the same "list of roads" the suite already implements, ordered differently because the deadline is harder.

If that route cannot be guaranteed, the argument flips: keep .NET, deploy it beside ServiceSuite on IIS, and port connections.ts's model rather than its code. The tenancy design in §6 is language-independent; it is the discipline that has to carry over, not the syntax.

§ 6Making it reusable across the ecosystem

A Micro Eazy client buying "the USSD product" should get a shortcode, a row in a registry, and their own menu — with no fork, no redeploy, and no second server. Three changes get there, and the first one is already sitting in the request payload.

6.1 · serviceCode is the tenant key, and it is free

Africa's Talking already tells you, on every single request, which shortcode the customer dialled. One channel per lender, one callback URL for all of them, and the tenant is request.serviceCode. This service captures the field in UssdRequest and uses it exactly once — to write it to a log line. 

// The registry. One entry per lender — mirrors ORGS in connections.ts.
export const CHANNELS = {
  "*384*4001#": { slug: "micromart",
                  entities: [3002, 3005],
                  conn: "SERVICESUITE_CONN_MICROMART" },

  "*384*4002#": { slug: "axe",
                  entities: [3003, 3004],
                  conn: "SERVICESUITE_CONN_AXE" },

  "*384*4003#": { slug: "njb",
                  entities: [3],
                  conn: "SERVICESUITE_CONN_BUYSIMU" },
};

// Resolution becomes a lookup instead of a guess, and F5 becomes impossible:
// a book that is not in this channel's `entities` cannot be reached from it,
// however many books the customer's phone number appears in.

Two things fall out of this immediately. The lender-selection menu can be intersected with the channel's entities, which closes F5 by construction rather than by a WHERE clause someone has to remember. And a single deployment serves every client, because the connection string, the entity list and the branding all hang off the same lookup.

Onboarding, after this change Request a channel from Africa's Talking, point it at the existing callback, add one registry row, add the connection string to the environment. No deployment, no code.

6.2 · One entity model, shared with the rest of the ecosystem

The registry above is deliberately the same shape as ORGS in connections.ts: a slug, a default EntityId, an env var holding the connection string, an env var that overrides the entity per deployment. The USSD service should not invent a second one. Where the two must differ is that a channel maps to a list of entities rather than one, because a lender with two books genuinely has two and the customer picks.

The rule the whole ecosystem already follows, and which this service should adopt verbatim: one connection per organisation, scoped by EntityId. Both Micromart books live on one SQL Server; the entity is what scopes the read, not the credential.

6.3 · Menus as data

The five level handlers encode Micromart's menu as C# control flow. The next lender will want a different order, different wording, Swahili, or a product tree one level shallower. Express the tree as data instead — a list of screens, each with a prompt, a source (static, or a query), and a target — and the level handlers collapse into one interpreter that walks the tree using parts.Length as the cursor. The screen budget of §1.5 becomes a property the interpreter enforces, with pagination for free.

This is also what makes the 0/00 convention testable. Today it is correct; there is nothing stopping the next edit from breaking it.
