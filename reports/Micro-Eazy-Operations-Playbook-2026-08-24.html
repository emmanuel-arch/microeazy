Four repositories, seven systems

The folder name is not the repository name

The local folder connected-suite pushes to a repository still called BirgenAI_LMS, and its Vercel project has never seen the folder name — Vercel builds from the repository. Renaming the folder was safe for exactly that reason. Do not rename the repository to match: that would re-point a live project and re-map every environment variable by hand, for no product benefit.

Why one deployment serves six systems

Because they share the two surfaces where a multi-tenant bug becomes a cross-lender data leak: auth and tenancy. Six separate deployments would mean six copies of session handling, the daily OTP, tenant resolution, the vault and RBAC — and five chances for one of them to drift. A subdomain here is a rewrite (src/proxy.ts), not a second application.

The Interchange is the exception, and deliberately so. It is a separate trust domain, not merely a separate product: it brokers between competing lenders, and the architectural claim is that no member can read the Registry from their own systems. That claim is worth a second deployment and a second database. See 06.

02

Local

Starting the estate

Everything runs from the meta-repo root, C:\GIT\MICRO EAZY. Four commands cover the normal day. 

# From C:\GIT\MICRO EAZY — the meta-repo root

npm run doctor       # is this machine ready? checks submodules, deps,
                     # env files, free ports, required variables

npm run bootstrap    # npm install in every system, in sequence

npm run dev          # start every system at once, colour-tagged output
npm run dev interchange   # …or just one

npm run build        # production build of every system, sequentially
npm run start        # run those production builds

Keeping the pins in step

The meta-repo does not contain the systems; it pins them at a commit. That pin is the record of which combination constitutes a working estate — which was previously written down nowhere, and is precisely why a fresh machine could not reproduce one. 

npm run pull         # pull the meta-repo and check out the pinned commits
npm run sync         # pull each submodule to the TIP of its branch instead

# After sync, the pins have moved. Record the new combination:
git add connected-suite interchange pwa
git commit -m "Bump the pointers"
A change spanning two systems is two pull requests and a pointer bump

That is the cost of independent deployability, and it is worth naming rather than discovering. Push the system repository first, then bump the pin in the meta-repo. A pin bumped to a commit that was never pushed will check out on your machine and on nobody else's.

Ports, and what to do when one is taken

npm run doctor reports a busy port before npm run dev fails on it. Two systems both defaulting to 3000 is the single most common way a local ecosystem stops booting — claim the next free port in portMap before writing a new registry entry, not after.

The Interchange needs its database started first

It is the only system with a preDev step. npm run dev runs it automatically; if you are starting the console on its own, run it yourself. 

# cd interchange/apps/interchange-console
npx prisma dev -d -n interchange   # detached; a no-op when already up
npm run dev                        # :3341

04

This release

What changed today

Three things, and one of them will take the product down if it deploys in the wrong order.

Run this before the deploy, not after

A new column, Org.systems, backs the per-lender system switch. The deployed code selects it on the first screen every staff member sees. If the code ships before the column exists, /suite throws for everybody. 

# against the PRODUCTION DATABASE_URL, before pushing to main
cd connected-suite
npx prisma generate
npm run db:push

1 — Lenders now hold systems, not the whole suite

There are now three gates in front of a system, and they compose by AND. Conflating any two of them is what makes access control impossible to explain to the person on the receiving end.

GateQuestionSet byWhere
EntitledDid this organisation buy it?Platform admin/platform
VisibleIs it part of this person's job?Their administratorStaffUser.access
EnteredDo they hold the right that opens it?Their roleRole.rights

/platform now carries a colour-coded toggle row per lender. The change is staged rather than instant — ticking three boxes is one decision, not three — and the Save button names what is about to be removed before you press it, because removals are the half that hurts.

Null means every system. An organisation that existed before this column is unrestricted and inherits systems added later. An empty array is a different, real value meaning no systems, and the launcher says so plainly rather than rendering a blank page.

Hiding a tile is a courtesy; the control is the refusal. Every satellite layout now checks entitlement server-side, so a lender whose Ledgerly was switched off cannot reach it by typing /books.

2 — Seven front doors

Each system's bare host now serves that system's own sign-in page rather than dropping straight into the console. The page holds both audiences at once: somebody already carrying a BirgenAI ID gets one button with their own first name on it, and somebody who only has the link gets the real email-and-password form — on that system's artwork, in that system's colour.

HostServes
lms.servicesuitecloud.com/suite/lms/login
analytics.servicesuitecloud.com/suite/analytics/login
peoplehub.servicesuitecloud.com/suite/hr/login
ledgerly.servicesuitecloud.com/suite/accounting/login
connectdesk.servicesuitecloud.com/suite/callcenter/login
microeazy.servicesuitecloud.com/microeazy — the borrower app; /login is the staff door

Two hosts deliberately have no staff door

microeazy.… keeps serving the borrower app at / because the installed PWA's start_url is that host — every home-screen icon already on a customer's phone opens there, and an installed base cannot be un-pointed. The lender staff door on that host is /login, which works today. The Interchange has no BirgenAI ID session to carry: it authenticates members by Ed25519 node certificate, so a "Continue as…" button would be a promise it cannot keep.

3 — The five satellites got a floor

The lending console has always sat on artwork while PeopleHub, Ledgerly, ConnectDesk and the Analytics Studio sat on flat grey — which is exactly why one of them looked like a product and the others looked like admin panels. They now share the console's canvas with a wash in their own accent, driven by the accent each system already declares. One shared image, seven distinct rooms, nothing new to keep in sync.

Separately: the lucide Sparkles icon has been removed from every live surface and the rule recorded, so it does not come back.

Why the Interchange returns 404

The Interchange repository has no package.json at its root. The Next application is at apps/interchange-console. A Vercel project left on the default Root Directory therefore finds nothing to build, produces no error worth reading, and serves a 404.

The fix: Project Settings → General → Root Directory → apps/interchange-console → Save. Then redeploy.

And then it fails to type-check — the second Interchange blocker

With the Root Directory fixed, the build gets far enough to fail differently: Module '@prisma/client' has no exported member 'PrismaClient', followed by two dozen implicit-any errors that are all downstream of it.

@prisma/client/index.d.ts contains one line — export * from '.prisma/client/default' — a re-export of a directory that prisma generate writes and npm install does not. It exists on your machine and is gitignored, so Vercel installs from the lockfile and gets the empty stub. Nothing exports PrismaClient, every Prisma call loses its return type, and every .map(h => …) becomes an implicit any under strict. One root cause, twenty errors.

The Connected Suite has always carried the generate step; the Interchange never did. Both now read: 

"postinstall": "prisma generate",
"build":       "prisma generate && next build"

Both, not either. postinstall alone is skipped when Vercel restores a cached node_modules without re-running the install; build alone re-generates on every local build for no reason. Together they cover both paths, which is why this is the shape the Suite already used.

And then it fails a third time — at “Collecting page data”

Failed to collect configuration for /api/authorise — [prisma] DATABASE_URL is not set.

That step imports every route module to read its configuration exports (runtime, dynamic, revalidate). Importing a route imported lib/prisma.ts, which built the client at module load and threw when the URL was absent. The client is now constructed lazily behind a Proxy, so importing the module costs nothing and the error fires at the first real query — where it is actually useful.

The general rule this is an instance of: a build must not depend on a secret being in scope. Build-time and run-time are different environments, and a build that only passes when production credentials happen to be present is one that fails on a laptop, in CI, and in every preview deployment.

Redeploy rebuilds the same commit

All three of the above were fixed in successive commits, and each one appeared to “come back” because Redeploy re-runs the commit that deployment was built from, not the tip of the branch. If a fix looks like it did not take, check the commit SHA at the top of the build log against git rev-parse --short origin/main before debugging anything else. A fresh deploy comes from a push — git commit --allow-empty -m "rebuild" && git push if there is nothing to change.

SUITE_COOKIE_DOMAIN is what makes the suite a suite

A session cookie set on lms.servicesuitecloud.com with no explicit domain is host-only — the browser will simply not send it to peoplehub.servicesuitecloud.com. Single sign-on works in development purely because every system is the same host. Miss this one variable and the symptom is not an error: it is being asked to sign in again on every subdomain, which reads as six products rather than one.

Leave it unset on preview deployments. A cookie scoped to .vercel.app would be shared with every other tenant of that domain.

Leave the six SUITE_*_ORIGIN variables for the in-repo systems (SUITE_LMS_ORIGIN, SUITE_HR_ORIGIN, and so on) unset. They exist to split a system onto its own deployment later; setting one now would point the launcher at an origin that does not exist yet. SUITE_INTERCHANGE_ORIGIN is the exception, because that system genuinely is elsewhere.

Data

Databases

You asked whether the Interchange should get a new Supabase database in production. It should — and not as a preference. It is the architecture's central claim.

SystemDatabaseHolds
Connected SuiteSupabase project A (existing)Lenders, borrowers, loans, staff, the vault
InterchangeSupabase project B (new)Members, consent records, the audit trail. No borrower record, no raw identifier
PWANoneTalks to the Suite over HTTP
PBX AuthSQL ServerTelephony authentication

Why not one database with two schemas

Because the Registry is a separate trust domain, not merely a separate concern. It brokers between lenders who are competitors, and the thing being sold is that no member can read the exchange from their own systems. Share a database and a Suite credential becomes a Registry credential — the audit trail, the consent records and every member's query history all sit one connection string away from the application those members are being asked to trust.

There is a mundane failure too: prisma db push from either repository would see the other's tables, and Prisma's opinion about tables it does not know about is not one you want to discover in production.

Creating it

  • New Supabase project. Region eu-central-1 or eu-west-2 — whichever the Suite already uses, so a call between them does not cross an ocean.
  • Copy both connection strings from Project Settings → Database. The Transaction pooler (port 6543) is DATABASE_URL; append ?pgbouncer=true. The Session / direct string (port 5432) is DIRECT_URL.
  • Push the schema and seed: 
    cd interchange/apps/interchange-console
# with the production URLs in the environment
npm run db:push
npm run db:seed
npm run operator -- create   # the first super-admin
  • Set both URLs in the Vercel project, redeploy, then run npm run verify:operator against it — it asserts that a hand-written session cookie is refused.
Two keys with very different blast radii

INTERCHANGE_SESSION_SECRET can be rotated freely: it signs everyone out and nothing more. INTERCHANGE_OPRF_KEY cannot — rotating it re-tokenises every borrower in the ecosystem, which invalidates every consent reference and every exposure record that points at one. Generate it once, store it where you store the vault master key, and treat losing it as data loss.

DNS

Nine records at the registrar for servicesuitecloud.com. Seven of them point at the same Vercel project, which is the whole trick.

Step one — add the domains in Vercel first

Add every hostname under Project → Settings → Domains before touching the registrar. Vercel then shows you the exact target and issues the certificate the moment the record resolves. Adding the DNS first just means waiting through a propagation cycle for a certificate that had not been requested yet.

08

Sequence

Go-live, in order

The order matters in exactly two places: the migration must precede the deploy, and the Vercel domains must precede the DNS. Everything else is independent.

  • Migrate the Suite database. The new Org.systems column, against production, before any code that reads it exists. 
    cd connected-suite && npm run db:push
  • Push the Suite. Vercel builds on push to main. This is the deploy that lights up connectedsuite.servicesuitecloud.com and the six doors. 
    cd connected-suite
git add -A && git commit -m "Seven doors, per-lender systems"
git push origin main
  • Create the Interchange database and push its schema — see 06.
  • Fix the Interchange project's Root Directory to apps/interchange-console, set its environment variables, and redeploy. The 404 goes away on that redeploy and not before.
  • Push the Interchange and the PWA. 
    cd interchange && git push origin main
cd ../pwa && git push origin main
  • Add all nine domains in Vercel, then the nine DNS records at the registrar. Wait for the certificates to issue — usually minutes.
  • Set SUITE_COOKIE_DOMAIN to .servicesuitecloud.com and SUITE_INTERCHANGE_ORIGIN to the live Interchange, then redeploy the Suite. Do this after the domains resolve: a cookie scoped to a domain that does not serve the app yet signs everybody out.
  • Bump the pins. Record which combination of commits is now live. 
    cd "C:\GIT\MICRO EAZY"
git add connected-suite interchange pwa
git commit -m "Live on servicesuitecloud.com" && git push
  • Walk it. Sign in at microeazy.servicesuitecloud.com/login, land on the launcher, open each system through its own door, and switch between two of them using the top-right menu without being asked for a password. Then switch a system off at /platform and reload the launcher — the tile should be gone, and typing its route directly should bounce you back.
Verified today

npx tsc --noEmit clean and npm run build exit 0 on the Connected Suite with all of the above in place; tsc clean on the Interchange console. npm run art:check runs and reports 4 plates passing, 2 failing. Nothing here has been run against production.

Not built

  • System selection at organisation creation. The toggles exist at /platform for an org that already exists. The self-service onboarding flow at /onboard does not yet ask, so a new lender starts unrestricted and is narrowed afterwards.
  • Package and systems are independent. Deliberately — a plan change should never silently take a system away — but it does mean the two can disagree and nothing flags it.
  • The Interchange is not in the switcher's session. Its tile links out and opens its own gate. Federating a BirgenAI ID into an Ed25519 member session is a real piece of work, not a configuration change.
  • PBX Authentication is a third-party repository (skegode), tracked read-only. Fork it before you need to push.

Where to look when this document is wrong. ecosystem/registry.json declares every system, port, command and deployment target, and every orchestration script reads it. ecosystem/ARCHITECTURE.md holds the boundaries that are load-bearing. src/lib/suite/ holds the seven systems, their hosts, their artwork and their entitlements — one list each, no second place. Adding an eighth system is one registry entry, one SUITE_APPS entry and one git submodule add.
